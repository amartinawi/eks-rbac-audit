Executive summary

Severity-weighted findings across EKS authentication and Kubernetes RBAC.

The most serious issue is ClusterRole “platform-readonly” is named read-only but grants cluster-wide Secret read and pod exec. Reading Secrets exposes ServiceAccount tokens, database and application credentials, and TLS private keys; the ability to exec into a pod turns any of those into code execution inside the cluster. Together they are a direct path to full cluster compromise, which is not what the people who were granted this role believe they hold. Also outstanding: ClusterRole “incident-debug” combines Secret read with pod exec (admin-equivalent); Operator-defined roles grant privilege-escalation verbs; Operator-defined roles can mint credentials, and 9 further issues. 13 IAM principals are mapped into the cluster through aws-auth, 7 of them with cluster-admin. The cluster's authenticationMode is API_AND_CONFIG_MAP. Findings by severity: 2 critical, 7 high, 4 medium, 2 low, 2 informational.

What is working well

  • Anonymous access is limited to the upstream-default system:public-info-viewer binding (health, version, and API discovery only).

HIGH

Operator-defined roles grant privilege-escalation verbs

rbac
Evidence
  • ClusterRole namespace-provisioner grants escalate, bind — bound to: ServiceAccount:provisioner (platform)
Remediation
  • Remove escalate, bind, and impersonate from these roles.
  • Where binding really is required (a controller reconciling RBAC), scope the rule with resourceNames to the specific roles it manages.
Impactescalate and bind let a principal award itself permissions it does not hold, defeating the RBAC ceiling entirely. impersonate lets it act as any other user, group, or ServiceAccount, including cluster admins — and the audit log records the impersonated identity, not the real one.

rbac

HIGH

3 automation principals hold permanent cluster-admin

eks-auth
Evidence
  • arn:aws:iam::111122223333:role/acme-ci-deploy-role (Kubernetes username “ci-deploy”) → system:masters
  • arn:aws:iam::111122223333:role/acme-jenkins-runner (Kubernetes username “jenkins-runner”) → system:masters
  • arn:aws:iam::111122223333:user/build-bot (Kubernetes username “build-bot”) → system:masters
Remediation
  • Replace long-lived credentials with short-lived, workload-specific identity — IRSA for in-cluster workloads, or a role assumed via an OIDC-federated CI token for pipelines.
  • Scope automation to the namespaces it deploys into with a dedicated Role; never system:masters.
  • Rotate the access keys behind these principals and review their CloudTrail and control-plane audit history for unexpected use.
ImpactCI runners, deployment pipelines, and repository credentials with standing system:masters turn a single leaked key or a compromised build into total cluster takeover. These credentials typically live in CI variables, are readable by everyone who can edit a pipeline, and are rarely rotated.
HIGH

3 IAM users hold cluster-admin through non-expiring access keys

eks-auth
Evidence
  • arn:aws:iam::111122223333:user/a.rivera (Kubernetes username “a.rivera”) → system:masters
  • arn:aws:iam::111122223333:user/m.chen (Kubernetes username “m.chen”) → system:masters
  • arn:aws:iam::111122223333:user/s.patel (Kubernetes username “s.patel”) → system:masters
  • IAM users authenticate with a static access-key pair. Unlike an assumed role, that credential has no session lifetime and no MFA requirement at the point of use.
Remediation
  • Move these people to federated access: an IAM role assumed through SSO with MFA, mapped into the cluster in place of the user.
  • Delete the IAM users' access keys once the role path is in use.
  • If a user must remain, require MFA on the key's permissions with an aws:MultiFactorAuthPresent condition.
ImpactA leaked or committed access key belonging to any of these users grants permanent, unconditional cluster-admin. There is no session expiry to limit the window and no MFA challenge at the point the key is used.

2 EKS access entries grant cluster-admin

eks-auth
Evidence
  • arn:aws:iam::111122223333:role/acme-break-glass → AmazonEKSClusterAdminPolicy (STANDARD)
  • arn:aws:iam::111122223333:role/acme-terraform-apply → AmazonEKSClusterAdminPolicy (STANDARD)

  • Prefer AmazonEKSEditPolicy or AmazonEKSViewPolicy with a namespace-scoped access scope where the full admin policy is not required.
  • Manage access entries in version-controlled infrastructure code so every change is reviewed.
ImpactAccess entries are evaluated by the EKS control plane before the aws-auth ConfigMap, so these grants are invisible to anyone auditing only Kubernetes RBAC or only the ConfigMap. They are full cluster admin all the same.

MEDIUM

Broad standing cluster-admin — 9 principals

rbac
Evidence
  • IAM users mapped to system:masters: a.rivera, m.chen, s.patel, build-bot
  • IAM roles mapped to system:masters: acme-platform-engineer, acme-ci-deploy-role, acme-jenkins-runner
  • EKS access entries granting cluster admin: acme-terraform-apply, acme-break-glass
  • cluster-admin is reachable through: ClusterRoleBinding cluster-admin → ClusterRole cluster-admin, ClusterRoleBinding eks:addon-cluster-admin → ClusterRole cluster-admin, ClusterRoleBinding service-mesh-operator → ClusterRole service-mesh-operator
Remediation
  • Reduce standing admins to the people who genuinely need continuous access.
  • Move the rest behind just-in-time elevation or a break-glass role with alerting.
  • Require SSO with MFA for every admin path and prefer role assumption over long-lived IAM users.
  • Schedule periodic access reviews against this report.
ImpactA large permanent admin set widens the blast radius of any single credential compromise and makes insider or lateral movement harder to distinguish from normal operation. There is no just-in-time or break-glass control at the Kubernetes layer.
MEDIUM

Cluster access is sourced from two places at once

eks-auth
Evidence
  • Cluster authenticationMode is API_AND_CONFIG_MAP: both EKS access entries and the aws-auth ConfigMap are evaluated, with access entries taking precedence.
  • The ConfigMap maps 13 principals; 4 access entries exist.
Remediation
  • Create an access entry for every principal still served by the ConfigMap, using the same username and groups.
  • Switch authenticationMode to API and delete the ConfigMap. Note this is a one-way change — API_AND_CONFIG_MAP cannot be restored afterwards.
ImpactConfigMap-based authentication has no per-principal audit trail, cannot express session policies or IAM condition keys, and a single bad apply can lock every administrator out of the cluster irreversibly.
MEDIUM

Control-plane logging is incomplete — audit, authenticator disabled

eks-auth
Evidence
  • Enabled log types: api, scheduler.
  • Missing: audit, authenticator.
Remediation
  • Enable the audit and authenticator control-plane log types on the cluster.
  • Ship them to a CloudWatch log group with a retention period that matches your incident-response window.
ImpactWithout the audit log there is no record of who read Secrets or exec'd into a pod, and without the authenticator log there is no record of which IAM principal mapped to which Kubernetes identity. An incident involving any finding in this report would not be reconstructable.
MEDIUM

The Kubernetes API endpoint is reachable from the entire internet

eks-auth
Evidence
  • endpointPublicAccess is enabled with publicAccessCidrs 0.0.0.0/0.
  • Every authentication weakness in this report is therefore reachable from any network.
Remediation
  • Restrict publicAccessCidrs to the office and CI egress ranges that need it.
  • Where possible enable private endpoint access and reach the API through a VPN, Direct Connect, or an SSM tunnel.
ImpactA public endpoint removes the network as a defence layer: credential stuffing, leaked kubeconfig reuse, and anonymous-access misconfiguration all become internet-exposed rather than requiring a foothold in the VPC.
LOW

ServiceAccount tokens are auto-mounted on almost every workload

serviceaccount
Evidence
  • 23 ServiceAccounts; only 2 explicitly set automountServiceAccountToken: false.
  • 9 of them are the per-namespace default ServiceAccounts.
  • 21 therefore mount an API token by default.
Remediation
  • Set automountServiceAccountToken: false on ServiceAccounts and pods that do not call the Kubernetes API.
  • Give the workloads that do call it namespace-scoped, least-privilege ServiceAccounts.
ImpactEvery pod without an explicit opt-out mounts a usable API token at /var/run/secrets/kubernetes.io/serviceaccount. A compromised container hands the attacker that token even when the workload never calls the API.

Interpreting this report

  • Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFORMATIONAL.
  • kubectl who-can does not evaluate pod subresources such as pods/exec, so exec rights were read directly from the ClusterRole and Role rules rather than from its output.
  • Findings marked unverified could not be confirmed against the EKS control-plane API — usually because the AWS CLI was unavailable or the auditing identity lacks eks:DescribeCluster.
  • Roles carrying the kubernetes.io/bootstrapping: rbac-defaults label are upstream Kubernetes defaults and are excluded from operator-defined rules.
